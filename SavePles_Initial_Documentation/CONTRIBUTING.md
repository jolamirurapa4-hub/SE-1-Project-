# Contributing to SavePles

Read the project brief, requirements and delivery plan before proposing changes.

## Changes

1. Open an issue or agree a scoped task with the maintainers.
2. Use a focused branch such as docs/research-workflow or feat/private-projects.
3. Explain the problem, proposed behaviour and affected requirement identifiers.
4. Update related documentation when a permission, workflow or data model changes.
5. Open a pull request with relevant verification and any unresolved limitations.

Keep language direct and specific. Distinguish implemented behaviour from proposals. Cite official sources for institutional procedures and current technical requirements.

## Review

A maintainer should review changes before merging. Permission and research-governance changes need review by an appropriate domain owner. Authors must not claim institutional endorsement, research validation or implementation completion without evidence.

## Data and assets

Use synthetic examples. Do not include credentials, participant records, private submissions, appointment evidence or identifying research data. Confirm permission before adding third-party code or assets. Keep the approved logo intact unless a branding change has been agreed.

No code or content license has been selected yet; confirm reuse terms with the project maintainers.
